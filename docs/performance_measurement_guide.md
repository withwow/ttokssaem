# 성능 측정 및 비교 검증 가이드 (Performance Measurement Guide)

본 가이드는 코드를 수정하지 않고 **[현재 성능]**, **[인덱스 추가 후 성능]**, **[쿼리 수정 후 성능]**의 3가지 시나리오별 성능 차이를 계량적으로 측정하고 비교하기 위한 구체적인 방법론을 제시합니다.

---

## 🛠️ 비교 검증 대상 3대 시나리오

1. **[시나리오 1] 현재 성능 (Before Tuned)**
   * 소스 코드: 기존 상태 (N+1 루프 쿼리 작동)
   * 데이터베이스: 인덱스 없음 (오직 PK만 존재)
2. **[시나리오 2] 인덱스 추가 후 성능 (Index Tuned)**
   * 소스 코드: 기존 상태 (N+1 루프 쿼리 작동)
   * 데이터베이스: 제안된 3개 인덱스 추가 완료
3. **[시나리오 3] 쿼리 수정 후 성능 (Query & Index Tuned)** (최종 목표)
   * 소스 코드: 단일 벌크 조인 쿼리로 변경 (`lastRuntimePlanStausEx` 활용)
   * 데이터베이스: 제안된 3개 인덱스 추가 완료

---

## 📈 성능 측정 및 비교 방법 3가지

### 방법 1. 애플리케이션 콘솔 및 파일 로그 분석 (가장 단순 & 안전)

본 프로젝트는 이미 모든 API 호출 시 `ElapsedTimer`를 통해 수행 시간을 기록하도록 설계되어 있습니다. 로그 파일이나 개발 서버 콘솔 화면에서 밀리초(ms) 단위의 소요 시간을 직접 비교할 수 있습니다.

#### ① 측정 단계
1. 프로젝트 루트에서 개발 서버 실행: `npm run dev`
2. 브라우저로 대시보드 진입 또는 API 직접 호출: `GET http://localhost:9503/v1/lastStudentStaus`
3. 서버 콘솔이나 `logs/trace.log` 파일을 확인하여 아래 형식의 로그를 찾아 기록합니다.

#### ② 확인해야 할 로그 예시
```text
[2026-08-09 11:32:01] [DEBUG] -  RESPONSE [0] /v1/lastStudentStaus (142ms) >> { ... }
                                                                   ^^^^^
                                                              이 부분의 시간 측정
```
* **비교 방식**: 각 시나리오별로 API를 약 5~10회 호출하여 평균 응답 시간(ms)을 기록하고 비교합니다.

---

### 방법 2. 데이터베이스 쿼리 프로파일링 (DB 레벨 상세 분석)

DBMS(MySQL 5.6) 엔진 레벨에서 쿼리가 소비한 정확한 시간과 CPU 점유 시간을 직접 확인하는 프로파일링 기능입니다.

#### ① 쿼리 프로파일러 활성화 (MySQL 접속 후 실행)
```sql
-- 프로파일링 기능 활성화
SET profiling = 1;
```

#### ② 비교 대상 쿼리 실행
각 시나리오 상태에서 문제의 쿼리들을 MySQL 클라이언트(Workbench 등)에서 실행해봅니다.
* **현재 상태**: 인덱스가 없는 상태에서 개별 `lastRuntimePlanStaus` 쿼리 실행
* **인덱스 추가 상태**: 인덱스를 추가한 후 동일한 쿼리 실행
* **쿼리 수정 상태**: 최종 제안된 통합 벌크 조인 쿼리(`lastRuntimePlanStausEx`) 실행

#### ③ 소요 시간 목록 확인
```sql
SHOW PROFILES;
```
결과 예시:
```text
+----------+------------+--------------------------------------------+
| Query_ID | Duration   | Query                                      |
+----------+------------+--------------------------------------------+
|        1 | 0.08924100 | SELECT * FROM runtimeplan WHERE memberid...|  <-- 시나리오 1 (인덱스 X)
|        2 | 0.00032100 | SELECT * FROM runtimeplan WHERE memberid...|  <-- 시나리오 2 (인덱스 O)
+----------+------------+--------------------------------------------+
```

#### ④ 상세 상태별 소요 시간 분석 (병목 확인)
```sql
-- Query_ID 1번에 대한 단계별 소요 시간 상세 보기
SHOW PROFILE FOR QUERY 1;
```
* `Sending data` 단계의 소요 시간을 비교하여 인덱스 적용 전/후 및 쿼리 단일화 전/후의 성능 향상을 분석할 수 있습니다.

---

### 방법 3. 부하 테스트 도구 활용 (대량 동시 요청 성능 및 처리량 측정)

사용자가 동시 다발적으로 유입될 때 서버가 초당 처리할 수 있는 요청 수(TPS)와 응답 지연 시간(Latency)을 측정합니다. Node.js 생태계에서 가장 가볍고 강력한 **Autocannon**을 추천합니다.

#### ① Autocannon 설치 (글로벌 설치)
```bash
npm install autocannon -g
```

#### ② 동시 요청 부하 테스트 실행 (10명 동시 접속, 5초 동안 요청)
```bash
autocannon -c 10 -d 5 http://localhost:9503/v1/lastStudentStaus
```

#### ③ 결과 지표 비교
테스트가 끝나면 아래와 같은 요약 표가 출력됩니다. 각 시나리오별로 지표를 기록하여 비교합니다.

| 측정 지표 | 시나리오 1 (현재) | 시나리오 2 (인덱스 추가) | 시나리오 3 (쿼리 최적화) |
| :--- | :--- | :--- | :--- |
| **평균 응답 속도 (Avg Latency)** | 예: 250 ms | 예: 35 ms | 예: 4.2 ms |
| **99% 응답 속도 (99% Latency)** | 예: 890 ms | 예: 92 ms | 예: 12.0 ms |
| **초당 처리량 (Req/Sec)** | 예: 32 req/s | 예: 240 req/s | 예: 1,890 req/s |
| **에러율 (Errors)** | 0 | 0 | 0 |

## 📝 검증 기록 양식 (추천)
위 세 가지 방법을 활용해 성능을 측정하고 아래와 같이 정리하면, 안전하고 설득력 있는 성능 개선 근거 자료(리포트)가 완성됩니다.

* **성능 개선 배율 계산**:
  $$\text{성능 개선율(\%)} = \left( \frac{\text{개선 전 소요시간} - \text{개선 후 소요시간}}{\text{개선 전 소요시간}} \right) \times 100$$
